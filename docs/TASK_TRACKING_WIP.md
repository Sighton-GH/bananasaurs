# Task tracking continuation map (staging only, not deployable)

Branch `feature/task-tracking` contains the staged implementation. The owners approved pushing it after verification passes, before Claude review. No merge to main is authorized. The dashboard says planning mode. Discord task-anchor posting and all task reminders remain off.

Implemented in this branch:
- Guild-scoped SQLite teams, tasks, optional dated children, reports, account bindings, memberships, and explicit president-role setting (migrations 0050-0052). Owner setup, create, versioned edit, an owner-only dashboard read, individual/multi-assignee picker, owner task form, Tasks board and Guide page.
- Binding and membership revocation routes. The owner-entered binding route only fetches a Discord member's existence; it does not prove account control and does not confer dashboard access. The dashboard is owner-only by design. Review whether dormant binding routes should be removed.
- Live Discord destination fetch for owner create/edit, including threads through their parent channel; live category fetch on Discord task commands. Owner setup diagnostics still use a gateway directory snapshot and should not be treated as send-time authority.
- `/task list` and `/task complete` declared by ADR 0099 as a narrow exception to ADR 0086, based on the owners' 2026-09-28 user message. List checks the invoking member, roles, stored team membership and current category. Complete moves the task to `awaiting_approval` with a versioned update and same-transaction audit. It does not approve a task or post a message.
- ADRs 0095-0100 record interim boundaries and choices. The command set has registration and subscriber tests; storage, HTTP and UI have focused tests. TypeScript project build and targeted tests/lint have passed. A dashboard package build passed with existing node-browser externalisation/chunk warnings. The earlier root build attempt hit a Node heap limit; later `tsc --build --force` passed with a 3072 MB heap. No live Discord test or visual UI inspection has been done.

Security checkpoint (ADR 0102): dashboard task reads are now owner-only. The pre-existing owner-entered binding checked member existence but did not prove account control, while the staged member read routes had treated it as enough to display task contents. The current lock removes that exposure; no member dashboard access is active. No member dashboard read reopening is planned; members use Discord only. The Discord interaction route is distinct and unaffected.

Approval checkpoint (ADR 0103): a deterministic `approveTaskForMember(scope, client, discord, actorId, taskId, expectedVersion, now)` service verifies a live Discord member, category and pinned role, plus explicit lead membership for subteam tasks. It then moves only `awaiting_approval` to `done` with CAS and same-transaction audit. The old unversioned child mutation helpers were removed. No Discord delivery.

Report checkpoint (ADR 0105): idempotent guild-scoped report storage by Discord message ID now exists and avoids audit-body leakage. An unanchored passive reply subscriber was deliberately not registered: a reply in a shared task destination is not enough to identify which task it updates, and the bot has not yet posted a task-specific anchor. Implement reply capture only after a persisted anchor or explicit member task selection is available. The tested repository function does not itself establish sender identity or thread authority.

Anchor checkpoint (ADR 0106): migration 0060 adds one task-specific Discord message anchor per task, with guild and channel keys. `recordTaskAnchor`, `taskForAnchor`, `tasksInDestination` are available from taskRepo. The first two are intended for validated send/reply paths; `tasksInDestination` provides candidates for clarification and never authorises a write. There is no anchor posting; the later reply checkpoint below registers a subscriber that remains dormant without anchors. The integrated migration journal orders 0053 before 0060, 0061 and 0070. The planned final response to an ambiguous update is a clarification, per the owners' decision.

Reply checkpoint: `createTaskReplySubscriber` is registered for `messageCreate` and accepts only an exact reply to a stored task-specific anchor, current category/destination, live Discord member and stored team membership; message ID dedupes storage. `taskReplyCandidate` returns IDs only when ambiguous, not a task selection or authority. An ambiguous task-update candidate now reaches the assistant clarification path after live member access checks, with a single configured bot-facing behaviour. No task anchors are posted automatically in planning mode, so no active reply capture can happen unless a future validated sender has persisted the anchor.

Multi-assignee checkpoint (ADR 0107): migration 0061 adds guild-scoped task assignees and backfills existing primary `assignee_id` values. Create/edit accept `assigneeIds` (1-25 unique IDs on individual tasks) after checking stored team membership and live Discord members; edit replaces them atomically with a winning version CAS. The existing `assignee_id` remains the first assignee for compatibility. Discord completion and anchored reports accept any assigned member but still check current team membership. Owner UI uses multi-select. The planning mode remains on. The integrated migration journal and snapshot chain order 0053, 0060, 0061, 0070.

Anchor edit guard: a versioned task edit now refuses destination changes after an anchor is recorded. Moving an anchored task needs an explicit re-anchor workflow; title/due/assignment edits remain possible.

Owner setup UI checkpoint: the Tasks page now lists the gateway directory roles and configured president role ID from setup diagnostics. Only the owner can choose a role through the existing owner/CSRF route; role names themselves are not authority, and the approval workflow is still not exposed to members. A configured role outside the suggestions remains visible rather than silently resetting it. Removing the role still needs a deliberate owner UI control or the existing delete route.

## Integrated local branch checkpoint (2026-09-29)

This local `feature/task-tracking` branch incorporates the owner-only docs section, 13 sequential core patches, the reminder worker, and the MCP task tools. No push or main-branch merge was made. A role-gated `approveTaskForMember` service exists but still has no authenticated Discord interaction caller, so approval remains fail-closed. The owner MCP/model actor cannot approve a member task.
