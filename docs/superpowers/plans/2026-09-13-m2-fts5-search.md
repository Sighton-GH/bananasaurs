# Slice M2 — FTS5 search and permission-filtered citations — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: `opencode-delegate:opencode-driven-development` (the controller writes briefs from these tasks; an opencode model implements and reviews). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `searchMessages(scope, …)` returns ranked excerpts and citations over the archive, a citation never names a channel outside the caller's visibility set, purged content leaves the index in the same transaction as the purge, and an operator can search from the CLI.

**Architecture:** One FTS5 external-content virtual table over `archive_messages`, kept in sync by three triggers, created by a hand-written migration (ADR 0049). One raw-SQL repository function — the project's only one — whose `WHERE` names `guild_id` and the visibility set explicitly. One `VisibilitySet` type. Two operator commands (`archive search`, `archive reindex`).

**Tech Stack:** better-sqlite3 13.0.3 with `ENABLE_FTS5` (verified), Drizzle for everything except the FTS query, Zod, Vitest.

**Spec:** `docs/superpowers/specs/2026-09-12-mcp-operator-server-design.md` §7.3; `docs/superpowers/plans/2026-09-12-mcp-operator-server-plan.md` "Slice M2"; **ADR 0049 including Amendment 1** (hand-written migration, the trigger set, raw SQL in one place; Amendment 1 replaces D4, amends D5 with the SQL forms that were executed, and adds D7 `findMessage`) — **read the amendment; it overrides D4 entirely**; and **ADR 0046 D6**.

## Global Constraints

- **Read `docs/reports/briefs/SANDBOX_RULES.md` before running any command.** Explicit paths on every `rg` and `git`; gates by exit code; never read `.env`, `data/**`, `backups/**`. (`rg` may be absent from the shell — use the Grep tool with an explicit path and say so.)
- **No new dependency.** FTS5 is compiled into `better-sqlite3` (verified: `PRAGMA compile_options` → `ENABLE_FTS5`).
- **One hand-written migration, and only this one** (ADR 0049 D1). Its first line is `-- ADR 0049: …`. Every other schema change in this slice — there are none — would go through `npm run db:generate`.
- **Do not modify** `mod_rules`, `mod_cases`/`mod_case_events` (schema or writers), `setRuleMode`, `setRuleConfig`, `recordVerdict`, `packages/core/src/automod/**`, `packages/core/src/mod/**`, `packages/core/src/effects/gateway.ts`, or M1's `archive_*` table definitions in `schema.ts` (the FTS table is additive; the only edit to `schema.ts` is a comment). The observe window is running on two real guilds.
- **Guild scope (rule 2):** `searchMessages` takes `GuildScope` first; its SQL names `guild_id = ?`; a two-guild test with **colliding message ids** asserts that neither hits nor counts cross. The FTS table carries `guild_id` as a stored `UNINDEXED` column precisely so this is expressible in SQL.
- **Visibility (ADR 0046 D6, §7.3):** the filter is applied **in the SQL**, so an invisible channel contributes to neither the citation list nor `COUNT(*)`. `VisibilitySet` is always passed, never defaulted.
- **Zod at every boundary (rule 3):** the CLI args and any route-facing input.
- **Redaction (rule 4):** no new log field carries message text. An excerpt is never logged.
- **Break it and watch it fail:** the leak test (Task 3 Step 1) is written first and its red run is Task 3's first commit; the purge test (Task 3 Step 3) is written against a seeded, genuinely-deleted, genuinely-expired row (see that step).
- **Facts established by running the SQL, not by reasoning (ADR 0049 Amendment 1) — do not re-derive them:** `PRAGMA table_list` reports `archive_messages_fts` as `type='virtual'` and its four shadows as `type='shadow'`, so `allTables()` (which keeps only `type==='table'`) never sees them; `WHERE archive_messages_fts MATCH ?` is correct **even when the table is aliased** (`WHERE f MATCH ?` fails with `no such column: f`); a malformed query raises `SqliteError`; `ORDER BY rank`, `bm25()` (negative, ascending is best-first) and `snippet(archive_messages_fts, 0, …)` all work against D2's column order; `DELETE` and `UPDATE OF content` both maintain the index; `INSERT INTO archive_messages_fts(archive_messages_fts) VALUES('rebuild')` restores it.
- **Gates run alone, read by exit code:** `npm run typecheck`, `npm run lint`, `npm run test`.

- [ ] **Step 2: Write the migration.** `drizzle/0020_archive_fts.sql`, first line `-- ADR 0049: a virtual table cannot be declared in schema.ts, so this file is hand-written.`

```sql
CREATE VIRTUAL TABLE archive_messages_fts USING fts5(
  content,
  guild_id UNINDEXED,
  channel_id UNINDEXED,
  message_id UNINDEXED,
  content='archive_messages',
  content_rowid='rowid'
);--> statement-breakpoint
CREATE TRIGGER archive_messages_fts_ai AFTER INSERT ON archive_messages BEGIN
  INSERT INTO archive_messages_fts(rowid, content, guild_id, channel_id, message_id)
  VALUES (new.rowid, new.content, new.guild_id, new.channel_id, new.message_id);
END;--> statement-breakpoint
CREATE TRIGGER archive_messages_fts_ad AFTER DELETE ON archive_messages BEGIN
  INSERT INTO archive_messages_fts(archive_messages_fts, rowid, content, guild_id, channel_id, message_id)
  VALUES ('delete', old.rowid, old.content, old.guild_id, old.channel_id, old.message_id);
END;--> statement-breakpoint
CREATE TRIGGER archive_messages_fts_au AFTER UPDATE OF content ON archive_messages BEGIN
  INSERT INTO archive_messages_fts(archive_messages_fts, rowid, content, guild_id, channel_id, message_id)
  VALUES ('delete', old.rowid, old.content, old.guild_id, old.channel_id, old.message_id);
  INSERT INTO archive_messages_fts(rowid, content, guild_id, channel_id, message_id)
  VALUES (new.rowid, new.content, new.guild_id, new.channel_id, new.message_id);
END;
```

  Use `--> statement-breakpoint` exactly as the generated files do (check `0018`'s separators and copy the spelling); the migrator splits on that literal marker and not on `;`, so the trigger bodies' interior semicolons are safe. The journal entry is `{ "idx": 20, "version": "6", "when": <a millisecond timestamp **strictly greater** than the last entry's `1789337740258`>, "tag": "0020_archive_fts", "breakpoints": true }` — the journal stores no hash, and the migrator gates on `when`, so an equal or smaller value is **silently skipped** on a database that has already run `0019` and looks exactly like success. Add a test in `packages/storage/src/schema-invariants.test.ts` asserting the journal's `when` values are strictly increasing.

If it fails, stop and report: that means this machine's SQLite classifies them differently and the ADR needs revisiting. Then prove the migration actually applied: a one-off check that `PRAGMA table_list` in a migrated test database contains `archive_messages_fts`. Commit: `feat(storage): FTS5 index over archive_messages, hand-written per ADR 0049 (M2 task 1)`.

### Task 2: The three tests that pay for what the invariants cannot see (ADR 0049 Amendment 1 D4)

**Files:**
- Modify: `packages/storage/src/schema-invariants.test.ts`

No exemption is added and no existing helper is touched — `allTables()`
keeps only `type === 'table'`, and the FTS machinery is `virtual`/`shadow`.
Three tests replace the guarantee the invariants cannot give:

- [ ] **Step 1: The machinery is invisible for the reason we think.** Assert
  that `PRAGMA table_list` on a migrated database reports
  `archive_messages_fts` with `type === 'virtual'` and each of
  `archive_messages_fts_data`, `_idx`, `_docsize`, `_config` with
  `type === 'shadow'`. Comment: if a future SQLite reclassifies these as
  `table`, this test fails loudly and ADR 0049 is revisited — rather than
  the FTS table silently failing STRICT.
- [ ] **Step 2: The index cannot outlive its content.** Two guilds, colliding
  message ids, a row each. Assert both are findable by a raw
  `SELECT ... FROM archive_messages_fts WHERE archive_messages_fts MATCH ?`;
  delete guild A's row through `archiveRepo` (not raw SQL); assert A's FTS
  entry is gone and B's remains. This proves the triggers are attached and
  the external-content contract holds.
- [ ] **Step 3: The index carries its partition key.** Assert
  `archive_messages_fts` has a `guild_id` column (`PRAGMA table_info`) and
  that a `MATCH` query filtered by `guild_id` returns only that guild's
  rows. This is the replacement for the schema-level partition guarantee.
  Plus the journal test from Task 1 Step 2 (`when` strictly increasing).
- [ ] **Step 4: Gates, commit.** `npx vitest run packages/storage/src/schema-invariants.test.ts` green. Commit: `test(storage): prove the FTS machinery is invisible to the invariants, and that its triggers and partition key hold (M2 task 2)`.

```ts
/** The channels a principal may be shown. Always passed; never defaulted. For the MCP operator: every archive-enabled channel in the guild. */
export interface VisibilitySet { readonly channelIds: readonly string[] }
export interface SearchHit {
  readonly messageId: string;
  readonly channelId: string;
  readonly authorId: string | undefined;
  readonly createdAt: number;
  /** FTS5 `snippet()` over `content`, with the match marked by the delimiters below. */
  readonly excerpt: string;
  /** BM25; lower is a better match, as SQLite returns it. */
  readonly rank: number;
}
export interface SearchResult {
  readonly hits: readonly SearchHit[];
  /** Total matching rows **within the visibility set** — never the unfiltered count (§7.3). */
  readonly total: number;
}
export const SEARCH_SNIPPET_OPEN = '[';
export const SEARCH_SNIPPET_CLOSE = ']';
export const SEARCH_LIMIT_MAX = 100;
export const searchMessages = (
  scope: GuildScope,
  input: {
    readonly query: string;
    readonly visibility: VisibilitySet;
    readonly channelIds?: readonly string[];   // narrows within the visibility set; never widens
    readonly authorId?: string;
    readonly before?: number;
    readonly after?: number;
    readonly limit?: number;                    // clamped to SEARCH_LIMIT_MAX
  },
): SearchResult;
/**
 * `INSERT INTO archive_messages_fts(archive_messages_fts) VALUES('rebuild')`, then the index row count.
 * The rebuild is table-global — FTS5 has no per-guild rebuild — while the count returned is this
 * guild's. That seam is deliberate and is why the command is operator-only and its audit row names
 * the guild that asked: a reindex on a single-tenant deployment rebuilds everything, and saying
 * otherwise would be the lie ADR 0004 exists to prevent.
 */
export const rebuildSearchIndex = (scope: GuildScope): number;
/**
 * The row by id, including a purged one (ADR 0049 Amendment 1 D7 — M1 ships no by-id reader).
 * `content` is NULL and `contentPurgedAt` is set for a purged message; the tombstone is the point.
 */
export const findMessage = (scope: GuildScope, messageId: string): ArchiveMessage | undefined;
```

- [ ] **Step 1: The leak test, watched failing.** In `archive-search.test.ts` with `openMigratedTestDatabase` (copy `archive.test.ts`'s setup exactly): enable two channels, put one message containing `pineapple` in each, search `pineapple` with `visibility: { channelIds: [A] }`. Assert `hits` has length 1, `hits[0].channelId === A`, **and `total === 1`** — not 2. Write it, run it, watch it fail against an unimplemented module; commit the red run.
- [ ] **Step 2: Implement.** `read(scope, fn)` (`packages/storage/src/write.ts:91-93`) hands the callback a Drizzle `Db` and nothing else; the raw better-sqlite3 handle is `db.$client`, which drizzle types as `Database` (`node_modules/drizzle-orm/better-sqlite3/driver.d.ts:23`) but **which nothing in `packages/storage/src` uses today** — you are the first. Typecheck it early; if `$client` is not reachable at the type level, stop and report rather than casting through `any`. Two prepared statements sharing one `WHERE`:
  ```sql
  FROM archive_messages_fts f JOIN archive_messages m ON m.rowid = f.rowid
  WHERE archive_messages_fts MATCH ?   -- the table name, never the alias: `f MATCH ?` is `no such column: f`
    AND f.guild_id = ?
    AND f.channel_id IN (<visibility placeholders>)
    [AND f.channel_id IN (<narrowing placeholders>)]
    [AND m.author_id = ?] [AND m.created_at < ?] [AND m.created_at > ?]
  ```
  the hits query adding `snippet(archive_messages_fts, 0, '[', ']', '…', 12)`, `bm25(archive_messages_fts)` and `ORDER BY rank LIMIT ?`, the count query being `SELECT COUNT(*)` over the same `WHERE`. An empty `visibility.channelIds` returns `{ hits: [], total: 0 }` **without running a query** (an `IN ()` is a syntax error, and "no visible channels" is a real state). Parameterise everything — never interpolate the query string. A malformed FTS query must not throw out of the function — `MATCH '"unbalanced'` raises `SqliteError: unterminated string` (executed, not assumed): catch it and return `{ hits: [], total: 0 }` with a comment saying an operator's typo is a usage answer, not a fault. The `IN (…)` placeholder lists are built from the array lengths — a test asserts a two-channel and a five-channel visibility set both work, since that is where hand-built SQL usually breaks.
- [ ] **Step 3: The rest of the tests.** Two guilds with colliding message ids → neither hits nor `total` cross (rule 2). `channelIds` narrows within the visibility set and **cannot widen** it (ask for a channel outside `visibility` → zero hits). `limit` clamps at 100 and defaults sensibly; `before`/`after` bound `created_at`; `authorId` filters. Ranking: two messages, one with the term twice, assert the order. Excerpt: the term appears wrapped in `[`/`]`. **The purge test, set up so it can only pass for the right reason:** upsert a message with content, `recordDelete` it with a `deletedAt` of `now - 31d`, assert search finds it, run `expireContent(scope, now)` and assert it returns **1** (not 0 — a test that purges nothing passes vacuously), then assert search now returns zero hits **and** `findMessage` still returns the row with `content === null` and `contentPurgedAt` set. This is ADR 0049 D3's and Amendment 1 D7's joint promise. `rebuildSearchIndex` after a manual `DELETE FROM archive_messages_fts` restores every row. Also: an empty `visibility.channelIds` returns `{ hits: [], total: 0 }` and runs no query (assert via a spy or by the absence of a throw on a database where the FTS table has been dropped — say which you chose); a malformed query returns empty rather than throwing.
