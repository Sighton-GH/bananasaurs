## Verdict
SHIP-WITH-FIXES — the slice is well built and every gate is green, but the backfill's continuation collides with its own still-`running` job row on the `jobs_dedupe` index, so backfill stops dead after 100 messages, and two of the three D1 vetoes are absent from the backfill write path.

## Findings

- **[Critical]** `packages/core/src/archive/backfill.ts:99-101` (with `apps/daemon/src/runtime/guild.ts:317-325`, `packages/core/src/jobs/kinds.ts:213-215`) — the continuation is enqueued under `archiveBackfillDedupeKey(guildId, channelId)`, which is **the exact key the currently-running job's own row holds**. `jobs_dedupe` is `UNIQUE (guild_id, dedupe_key) WHERE state IN ('queued','running')` (`drizzle/0001_bright_the_leader.sql:2`), and `jobs.ts:91` uses `onConflictDoNothing()`, so the insert is silently refused. Verified by reading the index DDL, `jobRepo.enqueue`, and `JobWorker.runOnce` (`packages/core/src/jobs/worker.ts:128,153,158`) — `store.complete` runs *after* `handler.run`, so the row is `running` when the continuation is attempted. A channel with more than 100 messages therefore backfills exactly one page, leaves `backfill_state = 'running'` and a frozen cursor forever, and nothing anywhere says why. This is the precise failure `packages/core/src/mod/purge.ts:28-47` documents at length and avoids by keying every successor off the tick's own `jobId`. **Fix:** give `archiveBackfillDedupeKey` purge's two-shape form (`…:<channel>` for the first job, `…:<channel>:after:<jobId>` for every successor), pass `context.jobId` from `run(payload, context)` into `enqueueContinuation`, and add a test that drives two ticks through the real `jobRepo`.

- **[Important]** `packages/core/src/archive/backfill.ts:43-56` / `apps/daemon/src/runtime/guild.ts:313-333` — `BackfillPorts` has neither `guildArchiveEnabled` nor `isChannelExcluded`. The only gate on the backfill write path is `findChannel`, i.e. the `archive_channels` row. Consequences, both of which ADR 0046 D1 forbids on the live path: (a) if the operator removes a guild from `BANANASAURS_ARCHIVE_GUILDS` while a backfill job is queued, **the next page still lands** — D1's "writes no row for a guild not listed even if a row in `archive_channels` somehow exists" holds only for the subscriber; (b) a channel that is archive-enabled *and* in `log_excluded_channels` is refused by the subscriber but fully backfilled by the job. Verified by reading both port literals and grepping the handler for either check (absent). **Fix:** add both to `BackfillPorts`, check them before `fetchRecentMessages`, and test both directions.

- **[Important]** `packages/storage/src/repos/archive.ts:388-395` — `expireContent` selects candidates with `isNotNull(archiveMessages.content)`, so a deleted message whose `content` is NULL is **never** purged: its `archive_attachments` rows (filenames) and `archive_message_edits` rows survive indefinitely and `content_purged_at` is never stamped. This is not hypothetical: `packages/discord/src/rest/port.ts:298` maps `content: message.content === '' ? undefined : message.content`, so every backfilled attachment-only or embed-only message stores `content = NULL`. PRIVACY.md's new rows promise "Content removed 30 days after deletion" and "Attachments … Same as the messages they belong to". **Fix:** make the candidate predicate `deleted_at IS NOT NULL AND content_purged_at IS NULL`, and stamp `content_purged_at` whether or not there was text to null.

- **[Important, latent]** `packages/storage/src/repos/archive.ts:356-370, 397-404` — for a `case`-tier row, `caseClosedAtOn` returns `undefined` when the case is closed but has **zero `mod_case_events` rows**, and `expireContent`'s `case` arm treats `undefined` as "not due yet". The row then never purges, silently and forever. The same hole opens if a `mod_cases` row is ever deleted (there is deliberately no FK, `schema.ts` comment). Verified by reading both functions; nothing exercises the zero-event branch (`archive.test.ts` always seeds one event). Latent today only because no code path sets `status = 'closed'` (`packages/storage/src/repos/mod-cases.ts:463`). **Fix:** fall back to a `closed_at`-equivalent (or the case's `openedAt`) when a closed case has no events, and test that branch.

- **[Minor]** `PRIVACY.md:82-86` — the five rows never name `archive_message_edits`. The archive retains **previous versions of edited messages** indefinitely for a live message; "Archived messages from channels the owner enabled" does not tell a member that their pre-edit text is kept. **Fix:** one more row, or widen row 1's wording.

- **[Minor]** `apps/daemon/src/runtime/archive-expiry-timer.ts:41-49` + `daemon.ts:127-134` — the timer enqueues one `archive_expiry` job for **every allowlisted guild**, including guilds with no `archive_channels` row at all. On the two live observe-window guilds `/status` will now permanently read "1 queued" and `jobs list` gains a row a day; `daemon.integration.test.ts` had to be rewritten around it (PR-73). Harmless work, but it makes a previously meaningful "0 queued" signal noisy. **Fix:** skip a guild with no enabled archive channels.

- **[Minor]** `packages/storage/src/schema.ts:990` / `drizzle/0018_oval_cammi.sql:4` — `archive_attachments.attachment_id` is declared with the `snowflake()` helper but carries no format CHECK, and `schema-invariants.test.ts:72` cannot catch it because `attachment_id` is not in `SNOWFLAKE_COLUMNS`. **Fix:** add the check and the column name to the invariant set.

- **[Minor]** `packages/core/src/ops/commands/archive.ts:131-155` — `archive disable-channel` cascades away every archived message, edit and attachment for the channel, and its audit `after` records only `{ channelId }`. The audit row is the only record that destruction happened and does not say how much. **Fix:** include the message count in `after` (the port already computes it for `archive status`).

- **[Minor]** `apps/daemon/src/ops/wiring.ts:483-491` and `packages/http/src/test-support.ts:432-435` — `archiveLinkCase` maps the repo's `'preserved'` to `'already-linked'`, so both the CLI text and the audit row say a message is "already linked" when it is linked to no case at all. **Fix:** widen the port union by one arm rather than lying in the audit trail.

- **[Minor]** `packages/core/src/archive/backfill.ts:100` — the continuation is enqueued with `runAfter: ports.now()`, i.e. immediately. ADR 0046 D4 says "one *throttled* resumable backfill worker"; the only brake is a 429 plus the worker's backoff. Worth a deliberate delay or a note in the ADR that the job-poll interval is the throttle.

- **[Minor]** `packages/core/src/archive/subscriber.ts:80` vs `backfill.ts:82` — live ingestion stores `createdAt: event.receivedAtMs`; the backfill stores the true `createdAtMs` derived from the snowflake. The `archive_messages_channel_created` index therefore orders two populations on different clocks. The plan specified `receivedAtMs`, so this is a recorded choice, not a slip — but M2's search ordering will trip on it. A comment on the column would pay for itself.
