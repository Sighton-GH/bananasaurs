## Verdict
SHIP-WITH-FIXES — the shell, routing, and five migrations preserve every endpoint, body, and header; the gates are green (typecheck 0, lint 0, 2429/2429 with the 41 new tests); but the re-auth dialog keeps a typed password in React state after cancel, and cancelling re-auth now raises a sticky "The request failed: reauth-required" danger toast — both new, both small to fix.

## Findings

- [Important] `packages/dashboard/src/ui/ReauthDialog.tsx:20-29` — `password` is cleared only on submit (`setPassword('')` in `onSubmit`), never on cancel (button, Escape, backdrop). The dialog is permanently mounted by `SessionInner` and only toggles `open`, so the state survives; the next re-auth prompt opens pre-filled with the previously typed password, and it sits in memory for the life of the session. Rule 4 is about logs/storage, but this is the one place the dashboard holds a password outside a submit path, and it holds it indefinitely. — Verified by reading: `Dialog.Content` unmounts on close (no `forceMount`), but `useState` lives in `ReauthDialog`, which never unmounts. Not mutation-tested (review is read-only). — Fix: clear in the cancel path too (a single `close = () => { setPassword(''); onCancel(); }` used by the button and `onOpenChange`), and add a test: open, type, cancel, re-open, expect an empty input.

- [Important] `packages/dashboard/src/app/session.tsx:59-72` + `packages/dashboard/src/api.ts:77` — cancelling re-auth now shows a **danger toast** titled "The request failed" with message `reauth-required`. `apiFetch` throws `ApiError(401, { error: 'reauth-required' })` on cancel; `write` catches every `ApiError` and toasts `err.message`, which is the raw server code. Danger toasts never auto-dismiss. The old `App.tsx` let this rejection go unhandled (silent), so this is new user-visible behaviour, and it contradicts D4 copy ("errors say what failed and what to try") — nothing failed; the operator cancelled. `session.test.tsx:106` asserts this exact text, locking it in. — Verified by tracing `apiFetch` (unchanged) and running `session.test.tsx`. — Fix: in `write`, treat `ApiError` with `status === 401 && body.error === 'reauth-required'` as a neutral, auto-dismissing "Cancelled — nothing was changed" (or no toast), and amend the test. Same branch should map a failed `/api/reauth` (wrong password) to "Password not accepted. Try again." rather than the server code.

- [Important] `packages/dashboard/src/app/StateStrip.tsx:14-21` — when `/api/health` is in `error` (or still loading), the strip is silent on every page except Overview, which is the only place `DataState` shows the failure. On `/safety`, `/logging`, `/panels`, `/audit` a kill switch that *is* on, or a disconnected gateway, renders as "nothing held" — exactly the "quiet console that pretends" D4/D6 forbid. The read-only hold is correctly independent of health (it comes from `session.info`). — Verified by reading the render path; `Shell.test.tsx` never stubs a failing `/api/health`. — Fix: add a hold when `health.resource.state === 'error'` ("Health unknown: could not load the health summary — holds cannot be shown"), and a test for it.

- [Minor] `packages/dashboard/src/ui/ConfirmDialog.tsx:36-40` + `pages/safety.tsx:21-33` — the confirm button is not disabled while the write is in flight (`ConfirmDialog` takes no `busy`; `setConfirming(false)` runs in `finally`). A double-click on "Turn kill switch on" sends two `POST /api/killswitch` and writes two audit rows. — Verified by reading; the page's own buttons are `busy`-gated, the dialog's are not. — Fix: pass `busy` through to `ConfirmDialog` and gate both its buttons.

- [Minor] `packages/dashboard/src/app/session.tsx:44-53` — two writes that both hit 401 before either resolves overwrite the single resolver; the first promise never settles and its caller's `busy` flag sticks forever. Inherited verbatim from the old `Dashboard` (`App.tsx` @ f228198:170-178) and not reachable today because every page's buttons are `busy`-gated and only one page is mounted. Flag only so Slice 8 does not add a second concurrent writer. — Fix (when needed): queue resolvers, or reject the second `requireReauth` while one is pending.

- [Minor] `packages/dashboard/src/app/StateStrip.tsx:27` — `role="status"` on persistent page chrome that is inserted *with* its content. Live regions announce changes to an existing region; a region that appears already populated is announced inconsistently across screen readers, and it makes three `role="status"` regions on Overview (strip, toast region, `DataState` loading/degraded). Not a test collision today (no test calls `getByRole('status')` with the strip mounted). — Fix: `<section aria-label="Active holds">` (or `role="region"`), keep `role="status"` for the transient regions.

- [Minor] `packages/dashboard/src/styles.css:66-69` — `:focus-visible { outline: 2px solid var(--color-hold) }` puts the hold colour on every focused button and link. D4: "never decorative and never on a button." Plan-verbatim, so the plan and the ADR disagree; one of them should give. `Button.tsx:14` `hover:bg-danger` is a button-sized fill of the semantic colour ("neither appears as a fill larger than a chip"), and `bg-black/60` / `hover:text-white` are colours named outside `styles.css`. All plan-verbatim. — Fix: focus ring in `--color-ink`; danger hover as border/text only; `bg-canvas/60` for overlays and `text-canvas` for danger hover text — or amend D4 to name these exceptions.

- [Minor] `packages/dashboard/src/hooks/useResource.ts:21` / `ui/DataState.tsx:46` — the `degraded` state (D6) has no producer anywhere in the dashboard; only the `DataState` unit test sets it. Not wrong, but D6's fourth state is a type and a test, not a behaviour. Slice 8 should be the first to populate it (e.g. gateway disconnected on a page whose data is still served).

## Decorative tests

- `Shell.test.tsx` "exposes Sign out" — asserts a button with that name exists; it would pass if the button called nothing. `logout` is covered in `session.test.tsx`, but nothing proves the *Shell's* button is wired to it.
- `Shell.test.tsx` "the rail lists every built NAV entry … and names the guild" — the plan's `findByText('Bananasaurs dev')` was loosened to `findAllByText(...).not.toHaveLength(0)` because the Overview page also renders the name. It now passes even if `GuildIdentity` renders "Guild" forever. Scope the query to the `aside`/`banner`.
- `StateStrip.test.tsx` "renders nothing when nothing is held" — waits only for `fetch` to have been *called*, not for the resource to reach `ready`. If the strip wrongly rendered amber on `ready` with no holds, this test could still pass while the resource is `loading`. Whether `act` drains undici's `Response.json()` microtask chain before the assertion is not something I could establish without mutating the file (read-only review). Fix: render a probe that exposes `useHealth().resource.state`, or await the Overview text, before asserting the strip is absent.
- `pages.test.tsx` "turning off posts { on: false } with no confirmation dialog" — proves no `ConfirmDialog`, but the re-auth half of the claim ("only re-auth") is not exercised on the Safety page itself; it rides on `session.test.tsx` plus the server's `write.test.ts:155-166`. Acceptable, but name it.

Plan-required assertions missing: (a) "focus lands inside" is asserted for neither dialog — Radix does it (`FocusScope trapped`, `onMountAutoFocus`, verified in `node_modules/@radix-ui/react-dialog/dist/index.mjs:219-226`), but no test would catch `trapFocus`/`autoFocus` being dropped; (b) `ReauthDialog` has no test for Escape or backdrop cancelling; (c) `Field` — restructured under PR-37 specifically for `aria-describedby`/`aria-invalid` — has no test of that wiring; `login.test.tsx` only checks the `role="alert"` text exists.
