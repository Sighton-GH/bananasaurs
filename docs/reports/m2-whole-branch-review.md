## Verdict

SHIP-WITH-FIXES — the code is clean, the leak is genuinely closed in SQL and every gate is green, but `0020_archive_fts.sql` never populates the index it creates, and on any database that already holds `archive_messages` rows that turns the next edit or retention purge into `SQLITE_CORRUPT`; F1 is a merge blocker because a migration cannot be amended after it has run.

## Findings

- **[Critical]** `drizzle/0020_archive_fts.sql:1-23` — the migration creates an external-content FTS5 table and its three triggers but never runs `INSERT INTO archive_messages_fts(archive_messages_fts) VALUES('rebuild')`. On a database that already has rows in `archive_messages`, the index is empty **and stays empty**, and worse: the `_au` / `_ad` triggers then issue FTS5 `'delete'` commands for rows that were never indexed, which FTS5 rejects with `database disk image is malformed`. I probed the exact table/trigger shapes against the installed `better-sqlite3` (in-memory): a pre-existing row gives `MATCH` count 0 before rebuild and 1 after; `UPDATE m SET content=?` on a legacy row → `database disk image is malformed`; `DELETE FROM m` on a legacy row → the same; after a `rebuild` first, both succeed. Blast radius in this tree: `recordEdit` (`packages/storage/src/repos/archive.ts:206`) throws and the edit is lost; `expireContent` (`archive.ts:399`) purges **all candidates in one `write()` transaction**, so a single legacy row aborts the whole retention run, permanently, every run — ADR 0046 D3 silently broken; `disableChannel` (`archive.ts:91`) throws on its cascade. **Fix:** append `INSERT INTO archive_messages_fts(archive_messages_fts) VALUES('rebuild');` as the last statement of `0020_archive_fts.sql` (after the triggers), with its own `--> statement-breakpoint`, and a test that seeds `archive_messages` at 0019 and migrates through 0020.
- **[Important]** `packages/storage/src/repos/archive-search.ts:146-151` — the `catch` is unconditional and silent: it catches `no such table: archive_messages_fts` (the migration never ran), `too many SQL variables`, a drizzle `$client` regression and `SQLITE_CORRUPT` exactly the same way it catches an operator's typo, returning `{hits:[],total:0}` with no log line and no signal. Verified by reading (`catch { return { hits: [], total: 0 } }` — no error binding, no rethrow, no `logger`) and corroborated by the branch's own test comment at `archive-search.test.ts:138` ("chosen over the dropped-table variant"), which only makes sense if a dropped table also returns empty. Combined with F1 this is the production failure mode the brief predicted: `archive search` says "no archived message matches that search" on a database whose index is broken. **Fix:** narrow to the malformed-query case — inspect `err.code`/`message` for the fts5 syntax family and rethrow everything else, or at minimum log the non-syntax case through `safeLogFields` (`err.message` carries no member content; I read `packages/core/src/obs/logger.ts:97-125`).
- **[Important]** nothing anywhere checks the index — `doctor` has no FTS check, `scripts/restore.mjs` does no rebuild, and no runbook tells an operator to run `archive reindex` after a restore. I searched every `.ts`/`.mjs`/`.md`/`.sql` outside `node_modules` for `archive_messages_fts|reindex|rebuildSearchIndex`: the only hits are the migration, ADR 0046, ADR 0049, and the M2 plan. ADR 0049's Consequences claims reindex exists "so a restored backup … has a documented recovery" — the command exists, the documentation does not. **Fix:** one `doctor` line comparing `COUNT(*) FROM archive_messages_fts WHERE guild_id = ?` against `COUNT(*) FROM archive_messages WHERE guild_id = ?` (or an `'integrity-check'`), plus a line in the restore runbook.
- **[Important]** `apps/daemon/src/ops/wiring.ts:506-508` — `archiveSearch`'s visibility set is built from `archiveRepo.listChannels(scope)` and never from caller input. That is the single most security-relevant line in the slice, and it has **no test**: I searched `apps/daemon/src/ops/ops.integration.test.ts` for `archiveSearch|archiveReindex` and found nothing, and `archive.test.ts` drives the command against hand-written stubs. The repository test proves the SQL filters; the command test proves the flag is forwarded; nothing proves the two are joined by a visibility set the operator cannot widen. A regression that passed `input.channelId` in as `visibility` would keep every existing test green. **Fix:** one integration test — enable channel A, archive a message in A and one in a not-enabled channel B, assert `archive search` returns only A's and `total` is 1.
- **[Minor]** `packages/storage/src/repos/archive-search.ts:103` — the `IN` placeholder count is unbounded in code. In practice it is bounded by `archive_channels` rows (Discord caps a guild at 500 channels, SQLite's limit is 32766), and `channels` is always the intersection with the visibility set, so it cannot be inflated by the caller. But there is no cap and no test, and an overflow would be swallowed by the `catch` above as "no results" rather than an error. `channels` is also not de-duplicated.
- **[Minor]** `packages/storage/src/repos/archive-search.ts:161-171` / `packages/core/src/ops/commands/archive.ts:~370` — the rebuild-is-global / count-is-per-guild seam is documented in the doc comment (a code reader sees it) but nowhere an operator sees it: the summary is "rebuild the archive full-text index from archived messages" and the output is "reindexed N archived messages", both of which read as per-guild. The audit row `archive.index_rebuilt` records `indexedRows`, which is the guild count, not what was rebuilt.
- **[Minor]** `searchMessages` applies no `m.deleted_at IS NULL` predicate, so a message a member deleted in Discord stays fully searchable with its text for the 30 days until `expireContent` purges it. I believe this is intended (the archive exists for moderation review, and ADR 0046 D3 makes the 30-day window the retention rule), but neither ADR 0046 D6 nor design §7.3 states it, and no test pins it either way. Worth one sentence in the ADR and one test, so a later reader does not "fix" it.
- **[Minor]** `archive search` is `write: false`, so an operator's full-text search across every member's archived message content leaves no audit row at all. Consistent with every other read command, but this read is materially more sensitive than `config get`.

## Decorative tests

It would pass if the command forwarded the channel to a port that ignored the visibility set entirely. It duplicates the test at :449 and detects nothing the latter does not.
- `packages/storage/src/repos/archive-search.test.ts:144` — *"a malformed query returns empty rather than throwing"* — passes against the catch-all, so it cannot tell "the operator typed a bad query" from "the FTS table does not exist" or "the index is corrupt". It is the test that makes F2 invisible.
- `packages/storage/src/repos/archive-search.test.ts:366` — *"restores every row after the index is wiped"* — wipes with `DELETE FROM archive_messages_fts`, which is not the production scenario. The scenario that matters (table created *after* rows exist) is untested, which is why F1 survived four per-task reviews.
- **Untested requirement:** ADR 0049 D1 / the migration itself — no test migrates a seeded `archive_messages` through 0020 and asserts the index is populated. `schema-invariants.test.ts` has the migration-over-seed machinery (`seedAt0014`, the 0017 tests) to do it.

## Verified and clean

- **The observe window is untouched.** The branch diff names 19 files; none is `mod_*`, `packages/core/src/automod/**`, `packages/core/src/mod/**`, or `effects/gateway.ts`. `schema.ts` gains four lines, all comment (verified in the diff hunk). M1's `archive_*` definitions are unchanged.
- **Trigger failure mode is contained.** A throw inside a trigger aborts the statement, which rolls back `upsertMessage`'s `write()` transaction; `packages/core/src/pipeline/pipeline.ts:126-145` isolates each subscriber in its own `try`, logging through `safeLogFields` and continuing, so the archive subscriber failing cannot stop automod or logging. Nothing in the enforcement path reads the index. Cost per message is three small index writes inside the existing transaction.
- **The citation filter holds, and so does the count.** `fromWhere` (`archive-search.ts:118-121`) is built once and shared by both the hits query and `countSql`, so the visibility and guild predicates cannot diverge. The leak test at `archive-search.test.ts:70` asserts `total === 1`, so it *would* fail if the count query lost the predicate — the specific check the brief asked for. I tried to construct a leak via `channelId` (intersected, :89 — an outside channel yields an empty set and an early return), an empty set (early return before `prepare`, spy-asserted at :132), `limit` (clamped 1..100, applies to hits only, `total` unaffected) and a malformed query (empty). I found none.
- **`guild_id = ?` is present in every statement touching the index**: the shared `fromWhere` (:102), and `rebuildSearchIndex`'s count (:168). The rebuild itself is table-global and says so.
- **No SQL string is caller-influenced.** Every user value is bound (`params`, :105-117); the only interpolations are the snippet delimiters/ellipsis/token count and `bm25`, all module constants, and the `?` *count*.
- **Edits never enter the index.** The FTS content table is `archive_messages` alone; `archive_message_edits` is a separate table with no trigger. `expireContent` deletes the purged message's edit rows (`archive.ts:433`), so purged text survives nowhere searchable. The purge/tombstone promise is tested at `archive-search.test.ts:334`.
- **No content in logs or audit rows.** `archive.index_rebuilt`'s `after` is `{ indexedRows }`; `archive search` is `write: false` so emits no audit row; `apps/daemon/src/ops/socket.ts` logs only errors, through `safeLogFields`, whose allowlist (`logger.ts:40-87`) contains no excerpt-shaped key.
- **`archive reindex` is gated.** `dispatch.ts:288` refuses any `write: true` command without `--confirm`; tested at `archive.test.ts:519`.
- **Global Constraints respected.** One hand-written migration with the `-- ADR 0049` first line; no new dependency; the four extra files (`ops/test-fixtures.ts`, `http/test-support.ts`, `automod-rule-lists.test.ts`, `wiring.ts`) are the plan's "four literals" implementing the two new port members; no `.ts` imports a `.tsx`. The journal entry is `{idx:20, when:1789337741258}`, strictly greater than 0019's, with a test pinning that.
- **Gates, run alone by exit code in the branch worktree:** `typecheck: 0`, `lint: 0`, `test: 0`. `npx vitest run` on the two FTS suites: 215 passed.
- **Nothing contradicts PR-80..PR-84.** The aliased-`MATCH`-on-table-name form, the absence of `VIRTUAL_TABLE_MACHINERY`, `findMessage` in `archive.ts`, `rawOf`'s cast, and the transaction-handle rebuild are all as ruled.
