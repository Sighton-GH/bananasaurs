## Verdict
SHIP-WITH-FIXES — the state machine, guild scope, capabilities, re-auth and validation are correct and I found no path to an impermissible transition, but the mode dialog's scope sentence is silent about the one combination that starts an observe clock on a rule that will not fire, and the three new `writeOrThrow` callers bypass the 401-outcome mapping Slice 7's round 2 fixed.

## Findings

- [Important] `packages/dashboard/src/pages/automod-rule.tsx:47-80` (`modeScopeSentence`) — When both `mode` and `enabled` change, or when `mode: 'observe'` is requested on a rule that is already disabled, the dialog states only the mode consequence. An operator who picks `observe` and unticks Enabled on a `not_started` rule is told "Starts this rule's observe window now. The two-week floor elapses on …" and nothing else; the server (`setRuleMode`, read at `automod-rules.ts:679-745`) will stamp `observe_started_at` **and** set `enabled = 0` in the same write, so the clock runs on a rule that matches nothing — the exact "observe data is worthless" shape ADR 0042 §1 cites. Same for `{ mode: 'test', enabled: false }` etc. — Verified by reading the function: `requestedEnabled` is only consulted when `requestedMode === undefined`; the body sent by `applyMode` (lines 136-139) carries both. — Fix: append a second sentence whenever `requestedEnabled !== undefined` alongside a mode ("…and disables the rule, so the window runs without it matching anything." / "…and enables it."), and when `requestedMode === 'observe'` on a rule whose resulting enabled flag is false, say so. PR-48 permits the transition; it requires the sentence.

- [Important] `packages/dashboard/src/pages/automod-rule.tsx:141-161, 187-200`; `packages/dashboard/src/pages/automod-rules.tsx:75-92` — The three `writeOrThrow` callers handle only `reauth-required`, 409, 400 and "any Error". Slice 7 round 2 (ledger, "the three 401 bodies the server can send map to three outcomes") lives only in `session.tsx`'s `write` (lines 108-124): `unauthenticated` → "Signed out" + `onLoggedOut()`, `invalid-credentials` → "Password not accepted", `ReadonlyError` → hold toast. A session that expires mid-edit on the new-rule form, mode dialog or config save now shows "The request failed: …" and leaves the operator on a page that looks signed in; a read-only instance shows the same generic danger toast instead of the hold toast. — Verified by reading both files and `rg -n writeOrThrow packages/dashboard/src/app/session.test.tsx` (no coverage). — Fix: give `Session` one shared `handleWriteError(err): 'handled' | 'unhandled'` that `write` and the three callers both use, or have `writeOrThrow` throw only for 400/409 and toast the rest itself.

- [Important] `packages/dashboard/src/pages/automod-rule.test.tsx` — PR-48's whole content is the sentence, and one of seven sentences is tested (`observing + test`). The `enforce`, start-window, rollback, generic, disable and enable branches, and the `enforce` radio being disabled when `eligibility.ok` is false, have no test (`rg -n "disabled|Starts this rule|Rolls this rule|Disables the rule|Enables the rule"` in the test file: no hits). `modeScopeSentence` is module-private so it cannot be unit-tested either. — Fix: export `modeScopeSentence` from `api/automod.ts` (a `.ts`, so it stays importable everywhere) with an `it.each` over the seven `(cutoverState, request)` pairs, plus one render test asserting `getByLabelText('enforce')` is disabled for an `ok: false` stub.

- [Minor] `packages/http/src/routes/automod.ts:189-200` — `automod_rule.mode_set` records `before: { mode, enabled }` / `after: <request>`. A `mode: 'observe'` request that stamps `observe_started_at` and moves `cutover_state` leaves no trace of either in the audit row; the plan asked for exactly this shape, so it is conformant, but an auditor cannot tell a window-starting call from a no-op from the row alone. — Fix: include `cutoverState` and `observeStartedAt` in `before` (the detail already carries them).

- [Minor] `packages/storage/src/repos/automod-admin.test.ts:159-197` — `countReviewedByRule`'s cross-guild assertion is `expect(countReviewedByRule(scopeB)).toEqual({})` with nothing seeded in guild B. `mod_match_reviews` and `mod_case_events` are both keyed `(guild_id, event_id)` (`schema.ts:962, 1176`), so a verdict on `e1` in guild B would join onto guild A's `e1` if the `guildId` join condition were dropped — and the test would still pass. — Fix: seed guild B with an event `e1` and a verdict and assert guild A still reads `{ 'rule-a': 2 }`.

- [Minor] `apps/daemon/src/ops/wiring.ts:205-283, 356-408` — none of the eleven production port members is exercised by any test (`rg` of the member names across `apps/daemon/src/**/*.test.ts` and `packages/core/src/**/*.test.ts`: no hits). `runAutomodDryRun` in particular — `findRuleIncludingDisabled → toAutomodRule → runDryRun` with `listFixtures(scope, {})` — is the one member whose test-support twin is a canned report, so the PR-47 route test would pass unchanged if the daemon used the enabled-only `findAutomodRule`. Typecheck covers the shapes; nothing covers the behaviour. — Fix: one `ops.integration.test.ts` case that disables a rule and dry-runs it through `opsPortsFor`.

## Decorative tests

- `automod.test.ts` "answers 409 not-eligible … and leaves the row alone" — asserts only `detail.mode === 'test'`; would pass if the refusal path wrote `updatedAt`, `cutoverState` or `enabled`. (By reading, `setRuleMode` returns before its `UPDATE`, so the property holds — the test just does not prove it.)
- `automod.test.ts` "toggles enabled and records before and after" / "replaces the config and records before and after" — read `tailAudit` rows but assert only `subjectType`/`subjectId`; `before`/`after` are stored as JSON strings (`effects.ts:360-361`) and never inspected. A route recording `after: { enabled: true }` for an `{ enabled: false }` request would pass.
- `automod.test.ts` "dry-runs a disabled rule" — passes against `test-support.ts`'s canned report, which never consults `enabled`; it proves the route does not 404, not that production replays a disabled rule (see Minor above).
- `cases.test.tsx` "renders the case and its events oldest first" — the stub's events are already in `at` order except for array position, so it does test the sort; fine. Listed for completeness: `MemberPage` "open first" is not asserted client-side, but the ordering is the server's (`mod-cases.ts:489-493`), which is correct.
